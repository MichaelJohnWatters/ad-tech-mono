Request flow across the platform — current state as of 2026-06-02.

Counterpart to architecture.d2 (which shows static topology). This one shows
the ordered path a single ad request takes from entry to render, including
the new publisher-adserver arbitration layer and the Prebid inbound demand
endpoint.

Three entry points feed two endpoints (auction core + ad render). Direct
sold tiers can short-circuit before the auction runs.

Key topology changes vs. pre-2026-06-02
---------------------------------------

1. publisher-adserver (port 8088) is the new browser-facing entry point.
   Sits in front of the SSP. Arbitrates direct-sold inventory per
   impression before any auction runs.

2. cmd/ssp is no longer always called. It's now invoked only when no
   direct-sold line item wins, as the programmatic demand source. The
   SSP itself is unchanged structurally.

3. Two ways into the exchange:
   - publisher-adserver → ssp → exchange (programmatic path, our publishers)
   - external Prebid Server → exchange /v1/prebid/openrtb2/auction
     (inbound Prebid demand; we act as a bidder for someone else's
     publishers via the bidder code "adtechmono")
   Both converge on the same auction core.

4. House is a second-pass. If programmatic returns no-bid, the
   publisher-adserver re-runs arbitration in house-only mode rather
   than letting the impression go unfilled.

5. New Redis keys:
   - publisheradserver:pacing:actuals:{line_item_id} — bumped per
     served direct impression; consumed by the even-pace controller
   - _adtm_uid cookie set by /v1/prebid/setuid for inbound Prebid
     bidder identity sync (30-day MaxAge)
